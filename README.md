# gcp-vertex-ml-pipeline

A **Vertex AI** training pipeline written with the **Kubeflow Pipelines SDK**:
ingest → train → evaluate → **metric gate** → conditional model registration,
for a customer-churn classifier (scikit-learn RandomForest).

The pipeline **compiles locally** to standard KFP IR (`pipeline.yaml`) with no
GCP account, and every component's logic is **unit-tested locally** — the
deploy step is the only part that stops at a manifest, deliberately (below).

## The pipeline

```
            ┌──────────┐   ┌────────┐   ┌───────────┐
 csv / gs://│  ingest  │──►│ train  │──►│ evaluate  │──► accuracy
            └──────────┘   └────────┘   └───────────┘        │
                                     model ──────────────┐   ▼
                                                         │ ┌────────────┐
                                                         └►│ metric_gate│
                                                           └────────────┘
                                                                  │ PASS only
                                                                  ▼
                                                          register_model
                                                          (deploy step)
```

Design decisions, and why:

- **The gate is a component, not an `if` buried in code.** Held-out accuracy
  must clear a threshold (default `0.75`) before `register_model` exists as
  anything more than a graph node — in the compiled IR it sits behind a
  trigger policy. A model that misses the bar is a training result, not a
  release. On the bundled data the model scores **0.817 accuracy / 0.895 ROC
  AUC** (majority baseline: 0.59), so the default gate passes and a stricter
  one (0.90) demonstrably fails — both directions are under test.
- **Train and evaluate use the same split seed.** Evaluate re-derives the
  split with the same `random_state`/`test_size`, so the rows it scores are
  exactly the rows training never saw. Letting these drift apart is a classic
  way to ship leakage-flattered metrics.
- **Training accuracy is reported, never gated on.** The gate consumes only
  the held-out number.
- **Components are self-contained.** Each `@dsl.component` carries its own
  imports and dependency pins, because the compiler serialises the function
  source into the IR — what compiles here is literally what Vertex AI would
  run in its containers.
- **The deploy step writes a manifest, not a deployment.** `register_model`
  records the model URI, accuracy and timestamp as a JSON deployment
  manifest. Promoting that to a real `aiplatform.Model.upload()` +
  endpoint deploy takes GCP credentials and a billing project; doing it
  implicitly from a laptop is exactly how surprise cloud bills happen. The
  production form is written out below.

## Data

`data/customers.csv` — 1,200 synthetic customers (age, income,
visits/month, tenure, churn label), generated by `data/generate_sample.py`
from a logistic process with a learnable signal and a deliberately
irrelevant feature (age). No real customer data anywhere near this repo.

## Run it locally

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt

python -m pytest -q              # 11 tests: component logic + pipeline compilation
python -m pipeline.pipeline      # compiles the pipeline -> pipeline.yaml
```

The tests execute the real component functions (ingest → train → evaluate →
gate → register) against file-backed artifacts, and assert the compiled IR
contains all five components plus the conditional trigger policy.

> Local execution note: the full pipeline has also been executed end to end
> with `kfp.local`'s SubprocessRunner — every task, including the
> conditional `register_model` step behind the gate, finished SUCCESS and
> produced the deployment manifest (accuracy 0.8167). That run takes ~3
> minutes, so it is kept as documented evidence rather than a CI test; the
> pytest suite covers the same component code paths directly.

## Going to Vertex AI

```bash
pip install -r requirements.txt google-cloud-aiplatform

# 1. Point csv_uri at a GCS copy of the dataset and submit the compiled IR:
python - <<'EOF'
from google.cloud import aiplatform
aiplatform.init(project="your-gcp-project", location="us-central1")
job = aiplatform.PipelineJob(
    display_name="customer-churn-training",
    template_path="pipeline.yaml",
    pipeline_root="gs://your-gcp-project-pipeline-root",
    parameter_values={
        "csv_uri": "gs://your-gcp-project-data/customers.csv",
        "accuracy_threshold": 0.75,
    },
)
job.submit()
EOF
```

## Layout

```
pipeline/components.py   ingest / train / evaluate / metric_gate / register_model
pipeline/pipeline.py     the @dsl.pipeline graph + compile entrypoint
pipeline.yaml            compiled KFP IR (regenerate: python -m pipeline.pipeline)
data/                    bundled sample dataset + its generator
tests/                   component unit tests + compilation test
```
